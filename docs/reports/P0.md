## 5 不一致之处、未解决的问题、需要决定的事项

### 说明与代码不一致（以代码为准）

1. F4 写"`load_manifest` 断言 `n==30`"。代码里 N=30 由 `Config.resolve` 限定；`load_manifest` 断言的是客户端数等于 `cfg.n`，以及每个分界恰好 10 台。
2. F11 写"`Backend.bottoms` 只为 `SPECS[model][3]` 中的三个分界预先建好前缀"。代码按实际用到的分界建：`hofl` 是 manifest 里的三个，`fedavg`/`fedprox` 是 0，`decomfl` 是层数。
3. F9 没有提 `sampler="auto"` 这个别名。
4. I1 把 `replay.py` 的容差写成"最大绝对误差 1e-7"。代码的判据是 `atol=1e-7` 加 `rtol=1e-5`。流程按说明的字面实现（最终状态的最大绝对差不超过 1e-7），比 `replay.py` 更严。
5. `ho-fl-profile` 只能在 CUDA 上运行，并且写死了 Qwen 的分界。说明没有提到这一点。
6. 上游自身不一致：`pyproject.toml` 的版本是 0.2.0，`ho_fl/__init__.py` 是 0.1.0。未改动。
7. 说明内部：§8 表格把"状态保存与加载"放进插桩提交，第 2 步写只加哈希和状态保存。我按第 2 步做，加载单独一个提交。

### 实现上偏离说明字面的地方

1. `ClientReport` 保存逐步损失（`losses`），`train_loss` 是由它算出的属性。原因：每轮的 `task_loss` 是对 K×E 个逐步损失一次取平均，先按客户端平均不能逐位复现。
2. 多了三个模块：`ho_fl/states.py`（状态读写，§6.2 把它放在 `train.py` 里）、`ho_fl/harness.py`、`ho_fl/testing.py`。
3. P0 没有为 `faults`、`links`、`probes` 建空模块，也没有加尚未实现的配置字段。`train_client` 接受 `cut` 参数，但与客户端自己的分界不同时会报错。
4. 黄金值流程：冒烟运行用 `python -m ho_fl.train`，在 `git archive` 导出的源码树里执行；插桩提交和当前代码的运行加了 `--save-state-rounds 3`，用来在不能逐位复现时计算最终状态的差；另外把上游原样提交也跑一遍，按日志字节比较。
5. 计时用 3 轮预检，没有先完整跑一次。超过 20 GPU 小时的网格"启动前写进报告"这条，改由时间预算控制，并在反馈里给出剩余运行的估计小时数。
6. 完成的 E0 运行不随代码版本重跑（每组结果旁边列出产生它的代码版本）；回归检查每个版本都重跑。

### 观察

主干是 BF16 时，LoRA 参数在 1e-7 量级的差别可以完全不反映在损失和评估指标上。本地把累加顺序颠倒后，3 轮内日志逐字节相同，只有最终哈希不同。所以 I1 里起决定作用的是最终参数哈希，逐轮 `task_loss` 相同只是必要条件。
